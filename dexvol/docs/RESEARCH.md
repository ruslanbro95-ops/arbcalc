# Этап 1 — Исследование источников данных

> Документ обязателен к прочтению перед изменением слоя `internal/sources`.
> ТЗ прямо требует: **не начинать основной код до завершения исследования источников.**

## 0. Дисклеймер о методе исследования (важно)

Часть исследования выполнена в изолированном контейнере, где **исходящий сетевой доступ
закрыт политикой egress** (разрешены только `proxy.golang.org`, npm/pypi/crates и API
Anthropic). Прямые запросы к `api.dexscreener.com`, `api.geckoterminal.com`, `api.llama.fi`
возвращают `403 connect_rejected` на уровне прокси.

Из этого следует:

* Сведения о лимитах и возможностях API ниже получены из **документации и публичных
  источников**, а не из живых запросов. Каждый факт снабжён ссылкой.
* **Числа покрытия (coverage %) в этом документе не проставлены.** Их нельзя получить
  без реальных запросов. Для их получения написана утилита `cmd/coverage`,
  которую нужно запустить на машине с открытой сетью (см. §7).
* В соответствии с п.22 ТЗ: **достижение ≥95% покрытия здесь не заявляется как
  установленный факт.** Это целевой показатель, который должен быть подтверждён
  прогоном `cmd/coverage` и занесён в §6 этого файла.

## 1. Что именно нужно от источника

ТЗ требует **поминутный календарный объём в USD** с покрытием ≥95% реального
торгового объёма токена. Это разбивается на четыре независимые задачи, и —
ключевой вывод исследования — **их обслуживают разные источники**:

| Задача | Что нужно | Кто это умеет бесплатно |
|---|---|---|
| A. Pool discovery | Полный список пулов токена во всех DEX сети | DexScreener, GeckoTerminal |
| B. Trade ingestion | Каждая сделка с timestamp, amount, side | Ноды напрямую (RPC); агрегаторы — частично |
| C. USD pricing | Цена токена и quote-актива | DexScreener, GeckoTerminal |
| D. Reference volume | Независимая оценка объёма для проверки покрытия | DexScreener `h24`, GeckoTerminal `h24` |

Попытка закрыть все четыре задачи одним бесплатным API — главная ловушка этого проекта.
Ни один бесплатный источник не закрывает B на пяти сетях с требуемой частотой.

## 3. Разбор кандидатов и почему они отпали как единственный источник

### 3.1 GeckoTerminal — точные сделки, но лимит убивает масштаб

Плюсы: бесплатно, **без ключа**, есть настоящий trades-эндпоинт
(`/networks/{network}/pools/{pool}/trades` — последние 300 сделок за 24ч),
есть минутный OHLCV.

Блокирующий минус — **арифметика лимита**. 30 запросов/мин, эндпоинт работает
**на один пул**. При целевом интервале 15 секунд это 4 опроса в минуту на пул:

```
30 req/min ÷ 4 опроса/мин = 7 пулов
```

**Семь пулов на всю систему.** Один токен со средней ликвидностью имеет 5–15 пулов.
То есть GeckoTerminal в режиме trades не тянет даже один токен целиком с нужной частотой.

Вывод: **не годится как первичный источник сделок.** Годится как (а) pool discovery,
(б) источник цены, (в) **независимый reference для замера покрытия** — там частота не важна.

### 3.2 DexScreener — отличное покрытие пулов, но нет сделок

Плюсы: бесплатно, без ключа, **300 req/min**, батч-эндпоинт на 30 токенов за запрос,
эндпоинт `/token-pairs/v1/{chainId}/{tokenAddress}` возвращает **все** известные пулы
токена сразу, поддерживает `robinhood` как chainId.

Арифметика лимита здесь наоборот комфортная:

```
30 токенов в одном запросе × 4 опроса/мин = 4 req/min на пачку из 30 токенов
300 req/min → сотни токенов без напряжения
```

Блокирующий минус: **нет per-trade эндпоинта.** Есть только скользящие агрегаты
`volume.m5 / h1 / h6 / h24` и счётчики `txns.m5.buys/sells`.

Почему это критично для нашего ТЗ: `m5` — **скользящее** пятиминутное окно, а не
календарная минута. Восстановить из него точный объём минуты 12:30:00–12:30:59
невозможно без потери точности: окно сдвигается, обновляется с лагом, и разность
двух последовательных `m5` даёт шум, а не объём минуты.

Вывод: **не годится как источник поминутного объёма.** Незаменим для pool discovery,
цены и reference volume.

### 3.3 Bitquery — правильные данные, неподходящий free tier

Free Developer plan: **1 000 points в месяц**, лимит **10 строк** в ответе,
**10 запросов/мин**, 2 конкурентных стрима; полноценный live WebSocket-стриминг
начинается с плана Pro ($99/мес). Лимит в 10 строк на ответ делает выгрузку
сделок бессмысленной. ТЗ запрещает платные API → **отпадает**.

### 3.4 Birdeye — 1 req/sec съедает бюджет за сутки

Standard free: **30 000 CU/мес при 1 req/sec**. При 4 опросах в минуту:

```
4 × 60 × 24 × 30 = 172 800 запросов/мес на ОДИН токен
```

Это в ~6 раз больше месячного бюджета на одном токене. **Отпадает** как основной,
может использоваться как дополнительный кросс-чек по Solana с редкой частотой.

### 3.5 Codex.io / Moralis — та же проблема бюджета

Codex free: 10 000 req/мес. Moralis free: 25 000 CU/мес, 4 req/sec.
Оба выгорают за 1–2 дня непрерывного мониторинга даже одного токена.
Годятся только как эпизодический reference в `cmd/coverage`.

### 3.6 Прямой RPC — единственный путь к ≥95%

Ключевое наблюдение по арифметике запросов. Для EVM `eth_getLogs` принимает
**массив адресов** и **массив топиков** за один вызов:

```
eth_getLogs({
  fromBlock: <последний обработанный>,
  toBlock:   "latest",
  address:   [pool1, pool2, ... poolN],   // ВСЕ пулы ВСЕХ токенов сети
  topics:    [[SwapV2, SwapV3, SwapV4]]
})
```

Это **один запрос на сеть на интервал**, независимо от количества токенов и пулов:

```
4 сети × 4 опроса/мин = 16 req/min на всю систему
```

Против сотен запросов у любого агрегатора. И покрытие при этом — **100% пулов,
которые мы обнаружили**, потому что мы читаем сам блокчейн, а не чужой индекс.
Coverage-риск смещается из плоскости «индексатор что-то пропустил» в плоскость
«мы не нашли пул» — а это решается pool discovery (§4) и проверяется §7.

Плюс: точный `timestamp` (по блоку), точный `tx_hash`, точный `log_index` для
дедупликации, точные `amount0/amount1` для BUY/SELL и объёма.

Robinhood Chain укладывается сюда же: это EVM L2 на Arbitrum Orbit, chain ID **4663**,
публичный RPC `https://rpc.mainnet.chain.robinhood.com`, mainnet с 01.07.2026,
экосистема DEX включает Uniswap. То есть **отдельный адаптер не нужен** — работает
тот же EVM-адаптер, отличается только конфиг сети.

### 3.7 Solana — честно признанное слабое место

У Solana нет аналога `eth_getLogs` с фильтром по множеству аккаунтов и диапазону
слотов. Доступные бесплатные пути:

1. `logsSubscribe` с `mentions: [poolAddress]` по WebSocket — даёт сигнатуры
   транзакций в реальном времени, но **одна подписка на один аккаунт**, и суммы
   свопа из логов надёжно не парсятся → нужен добор `getTransaction` на каждую
   сделку (дорого по кредитам на активном токене).
2. `getSignaturesForAddress` + `getTransaction` в режиме polling — то же самое,
   но с лагом и большим числом вызовов.
3. Helius `transactionSubscribe` (готовый распарсенный стрим) — с 07.04.2026
   **требует платный Developer plan**, WSS-трафик тарифицируется (2 кредита за 0.1 MB).
   ТЗ запрещает платное → отпадает.

Вывод: на Solana бесплатно достижимо либо полное покрытие с высокой стоимостью
вызовов, либо низкая стоимость с частичным покрытием. Реализация в
`internal/sources/solanarpc` идёт по пути 1 с батчингом `getTransaction`, и
**обязана** помечать данные как `DEGRADED`, если бюджет вызовов исчерпан —
вместо тихой потери сделок.

## 4. Выбранная архитектура источников

```
        ┌──────────────── POOL DISCOVERY (раз в N минут) ────────────────┐
        │  DexScreener /token-pairs/v1/{chain}/{token}   (все пулы)      │
        │  GeckoTerminal /tokens/{addr}/pools            (второе мнение) │
        └───────────────────────────┬────────────────────────────────────┘
                                    │ список пулов
                                    ▼
   ┌────────────────────── TRADE INGESTION (каждые 10–15 с) ──────────────────────┐
   │  EVM: eth_getLogs по ВСЕМ пулам сети одним вызовом                           │
   │       ethereum · bsc · base · robinhood(4663)                                │
   │  Solana: logsSubscribe(mentions) + батч getTransaction                       │
   └───────────────────────────────┬──────────────────────────────────────────────┘
                                   │ raw events
                                   ▼
                          DATA NORMALIZER  (→ domain.Trade)
                                   │
                                   ▼
                    DEDUP  (chain + tx_hash + log_index)
                                   │
                                   ▼
                    USD PRICING (DexScreener/GeckoTerminal, кэш ~15 с)
                                   │
                                   ▼
                            VOLUME ENGINE
```

Роли зафиксированы:

* **DexScreener** — pool discovery (первичный), цена, reference volume. 300 req/min.
* **GeckoTerminal** — pool discovery (второе мнение), цена (fallback), reference volume,
  выборочная сверка сделок в `cmd/coverage`. 30 req/min.
* **EVM RPC** — первичный источник сделок для ethereum/bsc/base/robinhood.
* **Solana RPC** — первичный источник сделок для solana, с явной пометкой деградации.

Дедупликация обязательна, так как один и тот же своп может прийти и из RPC, и из
агрегатора при кросс-сверке. Ключ дедупликации: `chain|tx_hash|log_index`
(для Solana: `chain|signature|instruction_index`).

Узкое место — **Solana**, всё остальное имеет кратный запас.

> До заполнения этой таблицы утверждение «покрытие ≥95% достигнуто» является

|---|---|---|---|---|---|---|
| _(заполнить)_ | | | | | | |

Про отсутствие абсолютного reference: полностью независимого «истинного» объёма
не существует — DexScreener и GeckoTerminal сами являются индексаторами со своими
пропусками. Поэтому методика §7 сравнивает **три** независимые оценки и трактует
расхождение как коридор неопределённости, а не как точную ошибку.

## 7. Методика замера покрытия (`cmd/coverage`)

1. Взять 3+ токена разного профиля: крупный мультипуловый (ETH/USDC),
   средний, и свежий низколиквидный.
2. Собрать наш конвейер в режиме «только сбор» ровно 1 час.
3. Параллельно снять `volume.h1` из DexScreener и `h1` из GeckoTerminal.
4. Посчитать:
   `Coverage_X = OurVolume / Reference_X × 100%`
5. Отдельно вывести **список пулов**, которые есть у reference, но нет у нас, —
   это прямой список пропущенной ликвидности.
6. Не путать «процент найденных пулов» с «процентом покрытого объёма»:
   отчёт обязан показывать вклад каждого пропущенного пула в USD.
